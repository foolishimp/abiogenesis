## Conditional Supersession

Only after docs acceptance, the S1 v4 design supersedes prior development
readings that:

- select the cumulative `ST-1` through `ST-4` MVP, C2A, W2-05, a 56-callable
  gate, or a horizontal sentinel as the next increment;
- treat an S1 development subject as `ABI5-ROOT-001`, `ABG5-S01`, a
  qualification subject, or a release subject;
- derive root selection from constants, fixture data, source/private imports,
  a caller receipt, a broad eager Product export, or a parallel selector;
- use system `tar`, `node:child_process` in Product verification, a rival
  installed verifier, ambient modules, or self-reported effect counters; or
- import Product resolve/install, Workspace, Catalog/View, Program/GF/
  `ExecutionBasis`, HoG, ABG, replay, SDK/CLI, or governor evaluation into S1.

The design does not supersede Product's root table, final one-family contract,
R1-R10 terminal predicate, accepted owner/runtime laws, or any scenario or
release requirement.

Rejected docs commits `6720c0d9`, `87d369d3`, `1e1e61af`, and `0d3c869f`
remain immutable evidence only. Their prose, ancestry, and implementation maps
are not carried forward by default.
