## 3. Core Position

Start with programming basics:

1. identify the entities of the system;
2. define the lifecycle of each entity; and
3. select one allowable truth path for each entity transformation.

Do not begin from services, files, frameworks, controllers, APIs, tickets, or
test harnesses. Those are subordinate realization choices.

The governing relations are regime-specific:

```text
pure immutable relation
  -> exact immutable inputs
  -> owner validation and construction
  -> typed immutable result or refusal

runtime mutation relation
  -> exact admitted prefix and authority
  -> owner transition candidate
  -> ABG admission
  -> durable event batch
  -> Event Calculus and replay projection

physical artifact relation
  -> exact immutable inputs and target policy
  -> owner validation and construction plan
  -> bounded filesystem or publication effect
  -> immutable manifest, provenance, or typed refusal
```

Not every entity transformation is a runtime lifecycle mutation. Pure Product
construction, validation, narrowing, conformance, and projection admit no
runtime event. Physical artifact effects produce their declared immutable
manifest or provenance boundary and must not be represented as traversal
events merely to share an adapter. ABG alone admits runtime mutation truth.

Two modules may not independently decide the same semantic relation or runtime
lifecycle state. Object identity, brands, caches, registries, controllers,
current store tails, caller state, and fixtures may support mechanics; none may
author semantic or lifecycle truth.

## 4. Programming Model

ABIogenesis realization is authority-conserving, entity-centric functional
domain modeling. Its runtime mutation subsystem is event sourced and
functionally reactive; its pure and physical-artifact relations retain their
own distinct effect laws.

ABIogenesis is a direct reference-frame evaluator and realization system. This
is the joined Product function, not a new named component. Product and

It combines:

- Domain-Driven Design for entities, stable identity, semantic ownership, and
  bounded contexts;
- functional programming for immutable values and pure decisions;
- event sourcing for admitted transformations as durable facts;
- functional reactive programming for projections and reactions over admitted
  event streams;
- Event Calculus for initiation, termination, inertia, clipping, declipping,
  and `HoldsAt`;
- typestate reasoning for lawful lifecycle transitions;
- hexagonal boundaries for storage, transport, and effects; and
- a functional core with a narrow imperative shell.

An admitted runtime entity is:

```text
stable entity identity
+ immutable admitted history
+ pure transition and projection law
= reconstructable lifecycle state
```

The runtime reactive cycle is:

```text
command
  -> pure transition decision
  -> authoritative admission
  -> durable event
  -> reactive projection
  -> consumer reaction
  -> optional new command
```

A reaction never mutates lifecycle truth directly. It returns through the
entity's sole command, transition, and admission path.

Pure immutable entities and carriers instead obey:

```text
declared immutable inputs
  -> owner validation
  -> deterministic construction or typed refusal
  -> caller-independent reconstruction
```

Physical artifacts obey:

```text
declared immutable inputs and target policy
  -> owner validation
  -> bounded physical effect
  -> exact immutable manifest and provenance or typed refusal
```

A physical artifact operation may use staging, exclusive creation,
content-addressing, idempotent preservation, or a Saga-style compensating
relation where one filesystem transaction is unavailable. Compensation is
effect recovery, not semantic rollback and not a second lifecycle authority.

### 5.4 Abstract Relation

Let `W_s` and `W_t` be immutable canonical topology witnesses for source and
target coordinates under the same owner-declared topology basis. Let `V_s` be
the typed carried source value and evidence. The complete owner-instanced
relation is:

```text
source frame and exact source coordinate
  + target frame and exact target coordinate
  + owner-declared topology and edge relation
  + typed carried value and evidence
  -> common continuous topology partition or structural refusal
  -> direct owner-local typed composition
  -> immutable target-owner candidate or owner refusal
  -> target-owner admission
  -> reconstructive projection
```

The pure topology part derives the maximal common rooted prefix and returns:

```text
preserved = maximal common prefix(W_s, W_t)
exited    = source-only suffix, ordered inner-to-outer
entered   = target-only suffix, ordered outer-to-inner
```

Every adjacent path relation must be owner-declared. The common callable ends
at one complete immutable `preserved`/`exited`/`entered` partition or one closed
structural refusal. It receives no carried domain value, evidence-transforming
function, candidate constructor, or owner refusal mapper.

The direct owner module statically composes that result with its own typed
atoms and carries `V_s` across the affected seams in deterministic order. That
owner-local pure composition returns one immutable target-owner candidate or
one owner refusal. No runtime request selects the atoms or composition. The
target owner performs admission after the owner-local pure relation returns.
Admission, events, effects, Event Calculus, and projection are outside both the
common partition and owner-local construction.

`preserved`, `exited`, and `entered` partition topology boundaries. The touched
set instead identifies materially affected seams. For an F_H resume, held
coordinate `H` and admitted successor coordinate `S` may have identical
topology witnesses while an evidence/input-coordinate seam remains touched.

### 5.6 Recursive Operator-Factorization Law

- **primitive**: one irreducible morphism with one semantic owner in the
  selected frame;
- **statically composed callable**: one closed installed Effect callable whose

- **projection**: a read-only interpretation of already constructed or
  admitted truth;
- **duplicate**: an existing function presented through another name or
  implementation; or
- **invalid**: hidden orchestration, rival authority, or behavior outside the
  selected Product.

Every alleged primitive declares its input object, output object, typed
refusal, effect boundary, semantic owner, selected frame, and the concrete

project primitive. Multi-owner behavior, or behavior that performs more than
one of select, validate, construct, admit, fold, and project, is a composition.

Factorization recurses through successively lower frames until every leaf is
one of:

1. an established external or language-library primitive;
2. an existing owner-domain primitive; or
3. an unavoidable physical effect boundary.

A higher-frame collapse is lawful only when it preserves exact inputs,
outputs, typed refusals, effects, authority, identity and provenance, ordered
admitted events, and replay result. Abstraction cannot amplify authority.
Cross-owner composition remains one statically composed installed Effect

#### 5.6.1 Closed operator algebra

The local realization algebra is:

```text
select      : FiniteSequence<A> x Predicate<A> -> exact<A> | absent | ambiguous
validate    : Raw<A> x Contract<A> -> Valid<A> | Refusal
derive      : Immutable<A> -> Immutable<B> | Refusal
transition  : State<A> x Command<A> -> Candidate<A> | Refusal
admit       : Prefix x Candidate<A> -> SuccessorPrefix x Admitted<A> | Refusal
traverse    : GTLGraph x Cursor x AdmittedBasis -> Proposal | Completion | Refusal
project     : ImmutableTruth x Selector -> Projection | Refusal
materialize : ImmutablePlan x PhysicalTarget -> Manifest | Refusal
```

These names classify functions; they are not a runtime instruction language.
Their laws are:

| Operator | Local law |
|---|---|
| `select` | Filters a multiplicity-preserving finite sequence or collection, then returns typed zero/one/many cardinality. Canonicalization may occur only after cardinality is known. It never converts candidates to a `Set` before selection, uses first match or fallback, or treats caller order as authority. |
| `validate` | Refuses before candidate construction, effect, admission, or traversal. It does not repair its subject silently. |
| `derive` | Is deterministic, immutable, side-effect free, basis preserving, and caller/process independent. |
| `transition` | Is owner-local and returns only a candidate/refusal. A candidate is neither a durable fact nor an effect authorization. |
| `admit` | Belongs only to the applicable admission owner. ABG runtime admission uses an explicit validated predecessor prefix and one expected-prefix atomic transaction. |
| `traverse` | HoG consumes the exact admitted GTL graph and ABG basis. It proposes structure and effects but cannot admit runtime truth or publish another Program. |
| `project` | Reads one explicit immutable carrier, artifact, or validated event prefix. It neither constructs a new semantic fact nor chooses a mutable current tail. |
| `materialize` | Performs only the declared physical effect, produces exact manifest/provenance, refuses overwrite/collision, and uses staging or compensation where atomic replacement is unavailable. |

Owner atoms remain ordinary typed functions. Pure Product, GTL, Validator,
HoG-decision, ABG-transition, Event Calculus, and replay atoms are not rewritten

calculus lifts and composes those atoms through exact-pinned Effect `3.22.1`:

```text

  A -> Promise<B | OwnerExpectedRefusal>

  A -> Effect.Effect<
```

#### 5.6.2 Installed definition-binding ABI

The S06 semantic relation remains `PublicInvocation<K> -> indexed owner
output`. `PublicInvocation<K>` is the common semantic descriptor required by
`REQ-P-PUBLIC-CONTRACTS-010`; it is not a physical-resource, artifact-locator,

therefore incomplete. One common type-indexed `DefinitionCall` joins the
admitted invocation to its explicit resource state without changing any of the
18 operation identities, 56 definition keys, owner requests, or owner outcomes.
The exact installed definition binding returns a closed Effect; it does not
return a plain value or Promise:

```text
OwnerTruth<K> =
  owner terminal truth
  | owner nonterminal truth

OwnerProgram<K> =
  Effect.Effect<
    OwnerTruth<K>,
    OwnerExpectedRefusalCause<K> | DefinitionExecutionFault<K>,
    DefinitionRuntime<K>

  OwnerTruth<K> | OwnerExpectedRefusalCause<K>
```

#### 5.6.2A Canonical resource-transition algebra

Every installed definition and executable GraphFunction leaf declares one
canonical resource topology as part of its owner contract or admitted GTL
boundary:

```text
ResourceTopology<I, O> = {
  inputs: CanonicalResourceSlotSet<I>,
  outputs: CanonicalResourceSlotSet<O>
}

ReadOnly(I, O) = identities(I) - identities(O)
Mutable(I, O)  = identities(I) intersect identities(O)
Create(I, O)   = identities(O) - identities(I)
```

These set relations are the only generic access/commit classification. A
`read`, `write`, `create`, `mutable`, or similar caller flag may describe an
owner contract for humans but cannot select mechanics. Two slots denote the
same resource only when their canonical resource identities are equal. A
mutable alias, branch, pointer, or named reference is a separate mutable
resource with its own identity and version; alias resolution does not collapse
it into its target.

The common carrier is:

```text
ExpectedResourceVersion<V> =
  ExactVersion<V>
  | Absent

ResourceBinding<R, V, P, G, S> = {
  resource: ReferenceDigest<R>,
  locator: CanonicalResourceLocator<R>,
  expectedVersion: ExpectedResourceVersion<V>,
  provider: ReferenceDigest<P>,
  capabilityGrant: ReferenceDigest<G>,
  expectedOwnerState: S
}

ResourceState<R, V, P, G, S> = {
  binding: ResourceBinding<R, V, P, G, S>,
  observedVersion: V,
  observedDigest: Sha256Digest,
  observedOwnerState: S
}

ResourceTransitionInput<I, O> = {
  inputs: CanonicalResourceStateSet<I>,
  outputs: CanonicalResourceBindingSet<O>
}

ResourceTransitionResult<I, O> =
  | {
      transitionDisposition: "unchanged",
      observedInputs: CanonicalResourceStateSet<I>,
      successorOutputs: Empty,
      commitEvidence: null,
      compensationEvidence: null
    }
  | {
      transitionDisposition: "committed",
      observedInputs: CanonicalResourceStateSet<I>,
      successorOutputs: CanonicalResourceStateSet<O>,
      commitEvidence: CanonicalResourceCommitEvidence,
      compensationEvidence: null
    }
  | {
      transitionDisposition: "recovery_recorded",
      observedInputs: CanonicalResourceStateSet<I>,
      successorOutputs: CanonicalResourceStateSubset<O>,
      commitEvidence: CanonicalResourceCommitEvidence | null,
      compensationEvidence: CanonicalResourceCompensationEvidence
    }
```

The type indexes name owner-declared slots; the values carry the dynamic exact
identities and versions. Input and output sets are duplicate-free and
canonically ordered. Every input requires `ExactVersion`. Every create-only
output requires `Absent`. An `I intersect O` row must carry the same resource,
locator, provider, grant, and expected pre-state on both sides. A definition
cannot recover a missing locator or state from a logical ref, path convention,
current process, ambient workspace, registry, fixture, or store tail.

`transitionDisposition` reports mechanics, not semantic success or refusal.
Read-only execution and any owner refusal before commit return `unchanged`.
`committed` must return the exact complete `O` set. `recovery_recorded`
preserves the exact visible output subset, commit evidence when one occurred,
and compensation or residue evidence; the matching owner `Rnn` alone decides
how that physical state appears in its indexed result or refusal. The generic
algebra cannot relabel recovery evidence as owner truth.

The transition laws are:

1. **Read-only** — identify and read the declared exact version; return no
   successor for that identity and perform no write.
2. **Same-resource mutation** — validate the exact pre-state, default to one
   writer, transform, compare-and-swap the expected version, commit once, and
   return the successor version. A mutable workspace defaults to a Git-backed
   before/after state carrying exact commit and complete tree identities. A
   different concurrency law requires an existing owner requirement and ABG-
   admitted safety basis; the generic provider cannot select it.
3. **Distinct-output derivation** — preserve every input; derive and create a
   separate content-addressed output under `Absent`; never overwrite an input
   or existing different output. Independent distinct outputs are mechanically
   parallel-safe only after declared output allocation proves their identities
   disjoint. An identity collision fails closed, or is idempotent only when the
   owner contract already declares identical-content idempotence.

Multi-resource work does not acquire a generic distributed transaction. One
owner expression must use an already selected atomic provider boundary or its
declared staging, publication, recovery, and compensation law. Effect `Scope`
may guarantee mechanical release and invoke an owner-selected compensation
callable; it does not invent Saga, retry, rollback, publication, or refusal
meaning. ABG expected-prefix admission remains the runtime atomicity law.

Owner refinements preserve stronger state rather than weakening the common
carrier:

| Resource owner/refinement | Required exact pre-state | Required successor or read evidence |
|---|---|---|
| Git-backed mutable worksite | repository/worktree identity, expected commit, complete before-tree digest, provider and grant | committed successor commit and complete after-tree digest, or exact refusal/compensation evidence |
| ABG durable event resource | `DurablePrefixCoordinate` plus matching `EventStoreReopenAuthority`/close handoff | expected-prefix transaction result plus successor prefix and owner-issued close handoff |
| immutable file/object/artifact | canonical locator plus expected object version/content digest | exact bytes/digest read, or create-only object identity/version and collision disposition |
| database/API transactional resource | canonical resource identity plus owner-selected transaction/version token | committed successor token/version and provider receipt, or exact refusal/compensation evidence |

`WorkspaceBinding`, Product, Program, GraphFunction, overlay, catalog, and
other immutable semantic carriers remain distinct from mutable worksite
versions. A new worksite observation does not mutate any of those identities.
Program entry threads the exact resource pre-state; selected implementation
effects perform only the declared transformation; the semantic owner decides
its result/refusal; and ABG admits the causal runtime truth when the governing
event-admission contract requires it. Resource mechanics never become GTL
topology, HoG traversal, ABG currentness, or Event Calculus truth.

Effect providers are stateless capabilities only. Their closed mechanical
surface is `identify`, `read`, `create`, `write`, `compareAndSwap`, `commit`,
and `compensate`; each installed definition receives only the subset it uses.
Providers cannot carry a current resource, selected version, semantic input,
actor, Run, cursor, or event prefix in `Context` or `Layer`. The installed host
provides the verified provider Layer and returns the existing `R = never`
definition program.

OS permissions, Git access, IAM, database grants, and remote API security
authenticate and enforce physical access outside ABIogenesis. A
`ResourceBinding` carries the resolved capability-grant reference, never a
credential, token, private key, or secret; its canonical locator is likewise
credential-free. ABIogenesis validates that the declared capability, provider,
actor, and resource scope match the admitted
definition. The resolved grant reference must equal one admitted invocation-
authority grant and cover that exact provider/resource/action scope; a provider
cannot widen it. ABIogenesis records only the required actor, resource pre/post
identity, GraphFunction, invocation, provider, causation, and provenance facts.
Secrets and credentials never enter Public identity, ABG events, replay,
projections, or evidence artifacts. External enforcement does not acquire
Product, admission, traversal, or lifecycle meaning.

##### Table 5.6.3-B2 - exact indexed owner-output closure catalog

An interior owner trace does not close an exact Public definition merely by
producing a domain carrier. Every class has one final owner relation `Rnn`
before `O_K`:

```text
Rnn<K>:
  owner terminal truth or owner nonterminal truth or owner refusal cause
    -> OwnerSemanticOutput<OwnerContractPacket<K>>
    = { outcomeKind: "result", value: ResultOf<K> }
      or { outcomeKind: "nonterminal", value: NonTerminalOf<K> }
      or { outcomeKind: "refusal", value: RefusalOf<K> }
```

The relation is semantic-owner construction, not Public projection. It selects
only fields declared by the exact indexed schema and obtains every reference,
digest, disposition, residual, provenance, evidence, and replay coordinate
from the preceding owner truth. It may not mint a coordinate, reinterpret an
event, catch an exception as a semantic refusal, or copy an obsolete Public
outcome. `B_K` owns request admission and `O_K` owns structural output
validation; neither constructs `Rnn`.

Source conservation is exact: read results echo the admitted request's
`caseKey`, source coordinate, and projection-basis coordinate; runtime results
and nonterminals use only ABG-admitted Event Calculus/replay coordinates;
artifact results use only the checked physical output plus its Product/ABG
admission; pure results use only the selected owner inputs and deterministic
owner carrier; attestation results use only the admitted subject, law, and
evidence. A `refDigestSchema` field is constructed from the matching owner's
reference and digest as one pair. Set-like arrays use the owning contract's
canonical order; ordered topology and lineage are never resorted. No `Rnn`
may derive identity from the external operation label alone.

For every `K`, `RefusalOf<K>` is the exact closed refusal schema declared by
the selected `OwnerContractPacket<K>`. `Rnn` preserves that owner carrier
object-identically. There is no cross-family normalized refusal carrier and no
Public refusal translation.

The shared refusal schema `{code, issuePaths, evidenceRefs}` applies only to
rows whose selected owner contract actually declares the shared
`refusalSchema`: currently `R01-R38` where applicable. For those rows the owner
selects `code` from the closed set stated below, supplies every causally
relevant evidence reference, and supplies exact JSON Pointer paths for the
refused relation. `R39-R40` instead preserve the live release owner's exact
`ReleaseSnapshotRefusal` carrier:

```text
{
  kind, schemaVersion, disposition, memberKey, code, message,
  requestedIdentity,
  qualificationBasisRef, qualificationBasisDigest,
  lawBasisRef, lawBasisDigest,
  verdictRef, verdictDigest
}
```

An invalid invocation belongs to `B_K`; an unexpected transport or adapter
failure belongs to adapter exit `70`. Neither may be collapsed into an owner
refusal. Where an existing lower carrier uses different names or shape, the
`Rnn` row's ordered cause list specifies that exact owner contract; it does not
authorize construction of a replacement carrier. Unlisted causes are a
construction refusal, not permission to add a catch-all.

##### Conservation relation

For every `K` in class `E`, the installed binding is acceptable only when the
ordered trace conserves all observations relevant to its regime:

```text
pure/read:
  exact result | nonterminal | refusal
  + reference/digest/provenance/evidence

artifact-effect:
  the above
  + exact admitted artifact-boundary fact and, where physical, exact bytes,
    paths, manifest, collision disposition, and recovery residue

runtime-mutation:
  the above
  + ordered admitted event bodies, causation, expected-prefix successor,
    Event Calculus state, replay, and fresh-process reconstruction
```

An implementation is not equivalent when it merely returns an equal terminal
JSON value while changing a refusal, physical residue, admitted event order,
causation, replay, or authority source. The factorization map is evidence for
this comparison and never an executable input to it.

### 10.6 TV5 Exact Binding

TV5 is the first implementation instance. It is a nested retry continuation,
not the definition of the common relation.

2. An attributed response is admitted. HoG derives successor cursor `S`, and
   the existing ABG `H -> S` successor predicate joins the two exact
   coordinates. `H` and `S` are not interchangeable.
3. `S` is the current traversal-route source. GTL derives target coordinate
   `T` or terminal disposition from the exact materialized C topology.
4. GTL owner adapters derive same-basis enclosing-retry topology witnesses for
   `S` and `T`. For TV5, the target retry path is a preserved prefix of the
   source path, `entered` is empty, and `exited` is ordered inner-to-outer.
5. The common computation returns only that immutable delta or a closed
   structural refusal. It does not consume completion evidence, construct an
   ABG candidate, classify F_H success, choose a route, mint a progress
   identity, or append an event.
6. Direct ABG owner construction consumes the delta and evidence and
   deterministically maps the complete exited partition to immutable
   predecessor-linked progress rows or one owner refusal. It does not expose a
   separately callable binary grouping seam where production has none. ABG
   admits the complete progress-and-route event batch in one existing
   transaction. ABG route verification consumes the same partition relation;
   replay and Event Calculus reconstruct the admitted outcome.
