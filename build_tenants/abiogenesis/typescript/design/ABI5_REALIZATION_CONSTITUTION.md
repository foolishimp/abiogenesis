## 3. Core Position

Start with programming basics:

1. identify the entities of the system;
2. define the lifecycle of each entity; and
3. select one allowable truth path for each entity transformation.

Do not begin from services, files, frameworks, controllers, APIs, tickets, or
test harnesses. Those are subordinate realization choices.

The governing relations are regime-specific:

```text
pure immutable relation
  -> exact immutable inputs
  -> owner validation and construction
  -> typed immutable result or refusal

runtime mutation relation
  -> exact admitted prefix and authority
  -> owner transition candidate
  -> ABG admission
  -> durable event batch
  -> Event Calculus and replay projection

physical artifact relation
  -> exact immutable inputs and target policy
  -> owner validation and construction plan
  -> bounded filesystem or publication effect
  -> immutable manifest, provenance, or typed refusal
```

Not every entity transformation is a runtime lifecycle mutation. Pure Product
construction, validation, narrowing, conformance, and projection admit no
runtime event. Physical artifact effects produce their declared immutable
manifest or provenance boundary and must not be represented as traversal
events merely to share an adapter. ABG alone admits runtime mutation truth.

Two modules may not independently decide the same semantic relation or runtime
lifecycle state. Object identity, brands, caches, registries, controllers,
current store tails, caller state, and fixtures may support mechanics; none may
author semantic or lifecycle truth.

## 4. Programming Model

ABIogenesis realization is authority-conserving, entity-centric functional
domain modeling. Its runtime mutation subsystem is event sourced and
functionally reactive; its pure and physical-artifact relations retain their
own distinct effect laws.

ABIogenesis is a direct reference-frame evaluator and realization system. This
is the joined Product function, not a new named component. Product and
Validator admit and validate recursive GTL declarations; GTL alone carries
graph, function, and topology meaning; one small HoG algebra evaluates them
through an Effect `3.22.1` fold and exact owner ports; ABG alone admits runtime
facts; and Event Calculus and replay reconstruct and project that truth.

It combines:

- Domain-Driven Design for entities, stable identity, semantic ownership, and
  bounded contexts;
- functional programming for immutable values and pure decisions;
- event sourcing for admitted transformations as durable facts;
- functional reactive programming for projections and reactions over admitted
  event streams;
- Event Calculus for initiation, termination, inertia, clipping, declipping,
  and `HoldsAt`;
- typestate reasoning for lawful lifecycle transitions;
- hexagonal boundaries for storage, transport, and effects; and
- a functional core with a narrow imperative shell.

An admitted runtime entity is:

```text
stable entity identity
+ immutable admitted history
+ pure transition and projection law
= reconstructable lifecycle state
```

The runtime reactive cycle is:

```text
command
  -> pure transition decision
  -> authoritative admission
  -> durable event
  -> reactive projection
  -> consumer reaction
  -> optional new command
```

A reaction never mutates lifecycle truth directly. It returns through the
entity's sole command, transition, and admission path.

Pure immutable entities and carriers instead obey:

```text
declared immutable inputs
  -> owner validation
  -> deterministic construction or typed refusal
  -> caller-independent reconstruction
```

Physical artifacts obey:

```text
declared immutable inputs and target policy
  -> owner validation
  -> bounded physical effect
  -> exact immutable manifest and provenance or typed refusal
```

A physical artifact operation may use staging, exclusive creation,
content-addressing, idempotent preservation, or a Saga-style compensating
relation where one filesystem transaction is unavailable. Compensation is
effect recovery, not semantic rollback and not a second lifecycle authority.

#### 5.3.2 Compounded-frame scenario proof law

An isolated component can be locally lawful while its composition violates a
coordinate, value, lifecycle-scope, prefix, owner, or projection relation.
Consequently, component-unit success cannot establish an integrated Product,
feature, wave, interface, or release claim.

Applicable reference frames contribute partial observations over one bounded
material-relation manifold. Coverage is the union of those observations;
admissibility is the intersection of their constraints. A bounded claim closes
only when every material relation and every touched cross-frame seam is
covered, or an uncovered relation is returned explicitly as a residual or
`out_of_frame`.

Every touched seam conserves or lawfully transforms this proof coordinate:

```text
entity identity
  + topology coordinate
  + carried value and digest
  + lifecycle scope
  + durable or artifact predecessor
  -> exact owner operation
  -> candidate or typed refusal
  -> owner admission or deterministic construction
  -> successor coordinate, value, scope, and prefix or artifact identity
```

The following local axioms govern proof selection:

| Axiom | Law |
|---|---|

A direct source import, unbound replacement core, wrapper test, or component test cannot establish reachability. |

### 5.4 Abstract Relation

Let `W_s` and `W_t` be immutable canonical topology witnesses for source and
target coordinates under the same owner-declared topology basis. Let `V_s` be
the typed carried source value and evidence. The complete owner-instanced
relation is:

```text
source frame and exact source coordinate
  + target frame and exact target coordinate
  + owner-declared topology and edge relation
  + typed carried value and evidence
  -> common continuous topology partition or structural refusal
  -> direct owner-local typed composition
  -> immutable target-owner candidate or owner refusal
  -> target-owner admission
  -> reconstructive projection
```

The pure topology part derives the maximal common rooted prefix and returns:

```text
preserved = maximal common prefix(W_s, W_t)
exited    = source-only suffix, ordered inner-to-outer
entered   = target-only suffix, ordered outer-to-inner
```

Every adjacent path relation must be owner-declared. The common callable ends
at one complete immutable `preserved`/`exited`/`entered` partition or one closed
structural refusal. It receives no carried domain value, evidence-transforming
function, candidate constructor, or owner refusal mapper.

The direct owner module statically composes that result with its own typed
atoms and carries `V_s` across the affected seams in deterministic order. That
owner-local pure composition returns one immutable target-owner candidate or
one owner refusal. No runtime request selects the atoms or composition. The
target owner performs admission after the owner-local pure relation returns.
Admission, events, effects, Event Calculus, and projection are outside both the
common partition and owner-local construction.

`preserved`, `exited`, and `entered` partition topology boundaries. The touched
set instead identifies materially affected seams. For an F_H resume, held
coordinate `H` and admitted successor coordinate `S` may have identical
topology witnesses while an evidence/input-coordinate seam remains touched.

   preflight proves them disjoint.

##### Table 5.6.3-B2 - exact indexed owner-output closure catalog

An interior owner trace does not close an exact Public definition merely by
producing a domain carrier. Every class has one final owner relation `Rnn`
before `O_K`:

```text
Rnn<K>:
  owner terminal truth or owner nonterminal truth or owner refusal cause
    -> OwnerSemanticOutput<OwnerContractPacket<K>>
    = { outcomeKind: "result", value: ResultOf<K> }
      or { outcomeKind: "nonterminal", value: NonTerminalOf<K> }
      or { outcomeKind: "refusal", value: RefusalOf<K> }
```

The relation is semantic-owner construction, not Public projection. It selects
only fields declared by the exact indexed schema and obtains every reference,
digest, disposition, residual, provenance, evidence, and replay coordinate
from the preceding owner truth. It may not mint a coordinate, reinterpret an
event, catch an exception as a semantic refusal, or copy an obsolete Public
outcome. `B_K` owns request admission and `O_K` owns structural output
validation; neither constructs `Rnn`.

Source conservation is exact: read results echo the admitted request's
`caseKey`, source coordinate, and projection-basis coordinate; runtime results
and nonterminals use only ABG-admitted Event Calculus/replay coordinates;
artifact results use only the checked physical output plus its Product/ABG
admission; pure results use only the selected owner inputs and deterministic
owner carrier; attestation results use only the admitted subject, law, and
evidence. A `refDigestSchema` field is constructed from the matching owner's
reference and digest as one pair. Set-like arrays use the owning contract's
canonical order; ordered topology and lineage are never resorted. No `Rnn`
may derive identity from the external operation label alone.

For every `K`, `RefusalOf<K>` is the exact closed refusal schema declared by
the selected `OwnerContractPacket<K>`. `Rnn` preserves that owner carrier
object-identically. There is no cross-family normalized refusal carrier and no
Public refusal translation.

The shared refusal schema `{code, issuePaths, evidenceRefs}` applies only to
rows whose selected owner contract actually declares the shared
`refusalSchema`: currently `R01-R38` where applicable. For those rows the owner
selects `code` from the closed set stated below, supplies every causally
relevant evidence reference, and supplies exact JSON Pointer paths for the
refused relation. `R39-R40` instead preserve the live release owner's exact
`ReleaseSnapshotRefusal` carrier:

```text
{
  kind, schemaVersion, disposition, memberKey, code, message,
  requestedIdentity,
  qualificationBasisRef, qualificationBasisDigest,
  lawBasisRef, lawBasisDigest,
  verdictRef, verdictDigest
}
```

An invalid invocation belongs to `B_K`; an unexpected transport or adapter
failure belongs to adapter exit `70`. Neither may be collapsed into an owner
refusal. Where an existing lower carrier uses different names or shape, the
`Rnn` row's ordered cause list specifies that exact owner contract; it does not
authorize construction of a replacement carrier. Unlisted causes are a
construction refusal, not permission to add a catch-all.

  exact result | nonterminal | refusal
  + reference/digest/provenance/evidence

  the above
  + ordered owner-leaf mechanical receipts
  + exact observed pre-version, reissued successor binding/handoff, and where

  the above
