## 3. What the formal self-host actually proves (verbatim-grounded)

This section replaces the earlier revision's "wrong bootstrap" verdict with the precise
one. All quotes are from completed `T-218` (revision 5).

**3.1 The certified loop contains no authoring.** DS-5's dependency column: *"exact
P4/I4, B5, and final S5 are **frozen**"* before stage one runs. B5 is *"one immutable
ABG-owned `self_build_program_manifest`… published as declaration/data in frozen S5"*;
DS-1F proves I4 can *"parse, bind, list, and start it against a bounded fixture root to
produce **one known artifact**."* The equivalence contract *"compares the
release-significant package identity, exports, compiled behavior, conformance result,
install/catalog manifests, runtime binding meaning, and declared B5 input/output
meaning. **Nondeterministic fields must be listed and shown irrelevant.**"* A pipeline
whose nondeterminism must be shown irrelevant to the artifact cannot contain meaningful
F_P work — if worker output mattered, the clause is unsatisfiable; since it must not
matter, the source was authored *before* the loop. So `C1 ≡ C2` is provable precisely
because it is a **packaging fixed point**: it certifies that a deterministic build
program produces the same artifact on the old and new runtime lines. All actual 5.0
construction (DS-2's runtime work, DS-3/DS-4's surfaces) happens *outside* the certified
loop, by ordinary hand-editing of S5 — unwitnessed by the very apparatus built to
certify "ABG builds ABG."

**3.2 The inversion, in the plan's own words.** GLC is excluded from the loop (A5-EX4:
*"G0/G5 do not participate in ABG C1/C2 compiler equivalence"*), and the campaign enters
only at DS-6 as *"one fresh full data-mapper campaign through installed I1/R5"* — i.e.,
as an acceptance test of the finished runtime. **Codex's plan: the campaign is a test
the new runtime must pass. F_H's model: the campaign is the builder that authors the new
runtime.** F2/F25's "ABG builds ABG" named the second thing; T-218 delivers the first.
That single reinterpretation of "build" — from *construct the software* to *run the
build step* — is the whole drift, and everything else (B5, C1/C2, R5:=C1, the DS
ordering) is downstream of it.

**3.3 What the fixed point is worth — the salvage.** The packaging fixed point is not
worthless: it dogfoods the runtime by executing ABG's own build as a declared GTL
program, and it checks runtime-line compatibility on the packaging path. But that value
is one cheap gate, not a milestone spine: **"pack the frozen source on the predecessor
install and on the candidate install; compare release-significant digests"** can join
the existing release discipline as a single qualification assertion whenever wanted —
no B5 carrier ceremony, no DS-1F…DS-5 chain, no `R5:=C1` identity coupling. That is the
honest salvage of DS-5, and it is demand-driven like everything else.

## 4. F_H's model, restated precisely (the reframe)

> abg/gtl → 4.6 is good enough → glc 0.1, install glc over working abg/gtl, use glc
> discipline spec-driven/ODD to build gtl 5.* beyond … it's just like data mapper, which
> we are currently getting good results for.

In toolchain terms: **ABG 4.6 = the stable machine/VM (frozen). GLC 0.1 = the
compiler-front-end + build-system + methodology, installed on it. GTL 5.\* = the next
thing you build with that toolchain.** Building GTL 5 is the data-mapper campaign pointed
at a new subject: spec → GLC/ODD lifecycle → AI worker F_P turns → F_D admission →
earned-depth proof → converged artifact. Self-hosting = the working stack *authoring* its
own successor under the discipline — operational dogfooding with admitted-evidence truth,
not a formal proof about packaging.

**The property trade, stated so it is ratified consciously (F_H queue item 5):** the
campaign model's artifact truth is **replay/digest provenance** (event ledger,
earned-depth, admitted evidence — this codebase's native truth model), not
**rebuild-reproducibility**. With F_P in the authoring loop, rerunning the build does not
reproduce the artifact; replaying the ledger reproduces the *truth about* the artifact.
Codex's plan offered a reproducibility-flavored guarantee, but only over packaging
(§3.1) — the choice was never actually reproducible-authoring vs provenance; it is
provenance vs provenance-plus-ceremony.

## 6. The evidence the drift's premise is false

The plan's load-bearing premise — "complete/rewrite the C runtime and formally self-host
before you can build forward" — against measured facts:

1. **The campaign runs on the 4.6 line as-is and gets good results** — real Scala, real
   sbt, mutation-tested, converged (rc.1: 3 retries/~56 min; rc.2: 2/~81 min; 64/64
   verified-restore kills). It needed neither `workflow.C` realized nor the strangler
   retired. *Bounded honestly (T-221's own evidence grade, review finding 7):* the
   full-campaign proof is rc.2-era `predecessor_evidence_only`; exact rc.3 carries Hello
   World plus the bounded odd_glc 0.1 live proof. The defensible claim is **candidate
   engine, ready for a bounded framework-shaped pilot** — which is what wave one is scoped
   to be. The plan's premise fails either way: nothing in this evidence says the C runtime
   must be rewritten before forward building.
2. **The capabilities exist and ran** — 31 source files carry the working
   spine/dispatch/consequence/foldback/handlers; four of seven C terms execute today.
3. **The deferred-strictness surface is small** — 7 files in `code/src` (9
   "transitional", almost all in one `c_call_enclosure.ts`; 2 "strangler"; 1 "rival
   export"). rc.2 exercised 86 `c_call_opened` / 86 `c_call_judged` — every arm the real
   engine took was enclosed. *Bounded honestly:* that is one scenario's path coverage,
   not proof the unenclosed path is unreachable; richer GTL-5 programs may reach shapes
   data-mapper never exercised. The right conclusion is not "the strangler is dead code"
   but "its retirement is small in code and correctly priced by demand" — which is
   exactly what the gap-event mechanism (§7.2) measures, and why DS-2's *up-front
   mega-leaf* form is the error rather than the work itself.

## 7. The constitutional-form argument

The correction is not merely lighter — it is the **law-conformant shape** under already-
ratified method, and the plan's form contradicts that method twice.

**7.1 Static enumeration vs discovered obligations — scope corrected (review finding 3).**
The discovery law governs **proof-surface obligation instances** whose cardinality depends
on delivered artifacts — PRODUCT.md verbatim: *"which tests instantiate a depth class,
which adversarial checks a delivered map implies"*. It does not prohibit planned
requirements, phases, or tickets; an 18-leaf delivery plan is **not unconstitutional by
form**, and rev 3 of this post overclaimed that. What survives, correctly scoped: the plan
pre-committed heavy leaves (the DS-2 mega-leaf, DS-4Q, A5-R1) whose right size is exactly
the kind of thing campaign evidence discovers, and the campaign model prices that work by
admitted demand instead. Oversized, not unlawful — the retarget stands on §3 and §6, not
on a constitutional-form charge.

**7.2 "Demand-driven" is the ratified intent loop — with its missing link named (review
finding 4).** A fair objection to "build `workflow.C` only if a GTL-5 program uses it":
programs *can't* use it — T-220's guard honestly rejects it — so demand could be
suppressed by the gap itself. The typed identities that resolve this exist:
`gtl-c-unrealized-workflow-lift` / `-batch` / `-retry`, classification
`semantic_not_realized`. **Honest status of the pipeline, verified in code:** the compiler
emits these as diagnostics and conformance projects them to `GtlProgramConformanceIssue`
rows (ruleRef `abg://gtl-program/c-algebra/semantic-not-realized`) — **no producer yet
admits them as ledger events**. Rev 3 overstated this as already-admitted evidence. The
bridge is therefore a named T-245 scaffold deliverable: the scenario declares the
conformance run inside worker turns so diagnostics ride the **admitted typed result** (the
EXECUTION DEFAULT path), with a code-level producer only if declaration cannot carry it.
Until the bridge lands, the loop runs supervisor-mediated — diagnostics read from campaign
results → intent → ticket — which is lawful but weaker: the earned-depth law cannot count
gap closure until gaps are admitted evidence. "Demand-driven" throughout this post means
that pipeline, at its honestly-stated maturity.

**7.3 F_D/F_P boundary.** The campaign model keeps authoring in F_P turns under F_D
admission — the constitutional seam. The formal loop achieves determinism by *excluding
F_P entirely* (§3.1): it doesn't violate the boundary, it evades the half of the system
the boundary exists to harness — and then certifies the remainder.

## 8. The corrected model's one real hazard — and its governing rule

Adversarial honesty about the campaign model itself; this is where it can go wrong, and
the rule that prevents it.

**8.1 Substrate/subject boundary.** Data-mapper's subject was external (Scala). GTL-5's
subject is *the builder's own next source* — so the standing law "fix the GTL/ABG
framework, never patch the scenario" becomes ambiguous mid-campaign: **which** framework —
the installed one running the campaign, or the subject source being authored? Unresolved,
this is exactly the drift channel by which workers (or codex) "fix" the live substrate
because "the framework is the bug." The rule the reprice should ratify:

> **During a GTL-5 campaign run, the installed substrate (ABG rc.x + GLC 0.x) is
> immutable law.** All authoring lands in the subject source tree. A substrate defect
> found mid-campaign is admitted as evidence and becomes a ticket on the predecessor
> service line — never a live patch under the campaign's feet. A substrate *capability
> gap* is a typed gap event and becomes GTL-5 subject content via §7.2.

**8.2 Which yields the real argument for settling 4.6 (row 11).** T-221 abandoned the
`4.6.0-final` tap on the premise that self-host supersession was imminent. Under the
campaign model that premise is gone *and* the model has a structural need T-221's
disposition can't meet: §8.1 routes substrate defects to a **serviceable predecessor
line** — somewhere a 4.6.x fix can lawfully land, re-release, re-install, and let the
campaign resume. `rc.3-permanent` gives substrate fixes no lawful home. The earlier
revision argued "don't build the future on a release candidate" (taste); the correct
argument is **the campaign model requires a patchable 4.6 line as its immutable-but-
serviceable floor** (structure). This re-opens the T-221 fork as a goal-reprice decision.

**8.3 Generality caveat, priced in.** The engine has converged on one subject domain
(n=1: a data mapper with an exhaustive typed UAT and a mature toolchain). A
language/runtime subject is categorically harder — its proof surface is partly the
conformance suite itself (row 9). So the first GTL-5 campaign wave is *also* the
engine-generality test, and should be scoped accordingly: a small, bounded first subject
item (§9 nominates `workflow.C`), not the whole GTL-5 surface in wave one.
