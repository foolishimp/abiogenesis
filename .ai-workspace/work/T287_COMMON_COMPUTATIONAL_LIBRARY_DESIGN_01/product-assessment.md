The Product's fifteen selected families are F01–F07, F09–F11 and F13–F17; their pre-RC scenarios are S01/S02/S03/S06, with S07 governing release. ## Supported decision

**`satisfied`: the requested library design is a lawful design-first activity within existing Product meaning.** Product already requires functional composition, one semantic authority per relation, explicit computation/effect ownership, valid reuse, preservation across recovery and bounded computational work. The design can factor the complete intended common capability basis now, using existing owners and accepted foundations. No Product or requirement change is identified as necessary merely to design that library.

**`indeterminate`: the final capability partition, source-wide duplication elimination, economic benefit and implementation conformance.** These require the other computational/recurrence assessments and independent evaluation of the actual candidate design. Existing generic helper names do not establish that their consumers share an admitted domain; a list of classes does not supply concrete reusable contracts.

The exact design outcome should be: a finite, source-grounded capability library whose selected entries state input/output and refusal domains, data and identity law, effect/lifetime/currentness obligations, accepted foundation composition, owning mechanism, actual consumers, composition constraints, and preservation/reproof obligations. Each recurrent computation receives consume/extend/replace/separate disposition. Two representative whole-path decompositions must demonstrate how the same entry serves different consumers without merging their semantic responsibilities. Design acceptance closes these decisions and obligations; execution plus appropriate assessment establishes actual outcomes later.

## Obligations to make commonisation useful

For every selected reuse edge, the design must explain the narrower domain that makes it lawful. Equal names, map shapes or similar source do not suffice. Each consumer supplies its exact input basis, expected output/refusal interpretation, permitted effects and invalidators. The shared contract conserves cardinality, ordering, identity and source qualifications. The owner interprets the result and admits any consequence.

Useful representative decompositions are:

1. Exact published artifact/declaration → canonical identity → verified immutable dependency closure → exact selection → static owner binding → physical install or admitted invocation → receipt validation → fresh projection. Installation reuse is one application of this mechanism chain, with physical install identity distinct from invocation identity.
2. Current admitted producer/input → scoped history acquisition → selected native context → owner-bound external computation → observed effect/result → ABG admission → incremental state → consumer preparation/correction → close/reopen and fresh read. The same selection/encoding/binding/history machinery is consumed at several roles without merging producer, assessor, effect or closure authority.

Explicit obligations are primary: the common design states which outcomes are permitted and what would falsify conservation. Actual execution determines which outcome occurred, including refusal, missing evidence and partial/unknown effect completion. A design should therefore not promise that the chosen helper makes the lifecycle green; it promises a determinate, source-grounded relation and the obligations by which behavior can be judged.

The method grounds these decisions in [DESIGN_MODULE UP-019](stdo://releases/v3.0.0-rc.1/standards/DESIGN_MODULE.md#computational-realisation-projection-up-019), [UP-023](stdo://releases/v3.0.0-rc.1/standards/DESIGN_MODULE.md#capability-and-foundation-selection-up-023), [decision-complete design](stdo://releases/v3.0.0-rc.1/standards/DESIGN_MODULE.md#decision-complete-symbolic-design) and [FOUNDATIONS shared machinery/composition](stdo://releases/v3.0.0-rc.1/standards/FOUNDATIONS.md#4-algebra). Each material capability needs a bounded foundation comparison, not an automatic preference for new local code or the incumbent. This Product assessment selects no new dependency and claims no exhaustive external-foundation search; that discovery is the assigned foundation frame's responsibility.

## Scope, sequencing and 5.1

The requested design comes first and should cover the intended common capability basis, not only the current installed failure. The previous computational binding's active boundary was preparation/history/native-material/continuation; that is useful input, not a reason to restrict or defer the now-selected broader library design. Goals, T-287 and the design index should route to the new concrete library design, with the existing installed lifecycle as an initial consumer after design decisions close.

Product [5.0 Compression Boundary](../../../specification/PRODUCT.md#50-compression-boundary) distinguishes correctness/authority defects from additional pure-helper compression. Duplication that changes admission, identity, currentness, replay or fresh-process behavior remains a 5.0 defect. Further semantically equivalent pure helper/layout/cache/test-mechanic contraction may be 5.1 implementation work. **That allocation does not defer or prohibit the user's requested design now.** The design should record both immediate correctness/dependency-required realization and later optional realization; it need not manufacture another all-helper implementation or release gate.

No concrete Product conflict was found in selecting this design first. A later decision that every optional helper contraction must ship before 5.0, new public capability/package, generic scheduler, broader graph generation or deferred human resume would require its own Product re-entry; none follows from the present instruction. Likewise C09's historical F_H/TV5 context does not restore native response/resume to 5.0.
