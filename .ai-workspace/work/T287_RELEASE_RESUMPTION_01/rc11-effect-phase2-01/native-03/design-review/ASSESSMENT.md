**Why coalescing belongs in R1.** `owned_process_state.ts:114–119` suppresses only a nested check while an entered probe token remains current. A current kill probe's continuation owns the signal and the finite KILL confirmation deadline; a deadline probe's continuation owns finishScope. After R1 starts rejecting superseded tokens, blindly starting a nested check can replace that token with a check token. The nested check can schedule another poll, while the now-stale kill/deadline return is rejected. The signal/deadline/drain obligation would then be lost. Retaining the existing token and letting its return decide against the updated state avoids that loss.

The guard does not cancel an explicit strengthening request, change a bound or declare absence. complete clears the token (`:122–124`); probed clears an accepted token before following its continuation (`:159–180`); the next ordinary check can therefore probe normally. Ordinary non-reentrant execution has no in-flight token at a separate check call and is unaffected. Physical probe attempts are still counted at entry and canceled tails before entry are not counted (`lifetime:215–233`, state:231). Actual call counts may differ from a buggy reentrant predecessor path; the requirement is truthful counts and preserved duties, not reproducing obsolete duplicate work.

The new controlled case at test:496 exercises exit during the **kill probe**, retains its token, requests one KILL and asserts 100ms/10ms waits, a 200ms cleanup bound and finite finalization. It is a meaningful behavioral case for this guard, not an action-list mirror. Deadline re-entry is supported here by source reasoning, not a separately executed sample. As before, no claim covers a host probe that never returns synchronously; Scope or coalescing cannot bound arbitrary blocked host code.
