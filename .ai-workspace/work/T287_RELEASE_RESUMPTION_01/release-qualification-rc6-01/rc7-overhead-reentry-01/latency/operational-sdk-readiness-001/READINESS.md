**The existing installed APIs support one acquired resource through construction, mechanical preflight, native start, completion and physical close. No SDK/library extension is needed for this ordinary author route.** Current operator controls do not yet compose the entire sequence, so this is supported API readiness, not a drop-in replacement or dispatch authorization.

The transition binder accepts actual borrowed selections. The separate read binder's reopen-only restriction therefore does not block a native start. This sequence retains the prepared call across preflight and invocation; merely replacing the cold CLI after a separate serialize/reparse/reacquire preparer would leave avoidable control work. Root must bind the future same-process mechanics before effects. It does not require a new approval controller. If a host really exits, ownership is gone and a later genuine acquisition is required. A prior reopen-based prepared call cannot simply have its resource field replaced: population must rebuild transport-steering, invocation identity and corresponding evidence under the acquired selection.

The owner relation remains exact. Copied/foreign selections have no module-issued custody; currentness observes the held store, path identity and extent; transition completion joins the same store and exact entry to its current successor. An SDK Promise also supplies none of the existing command recorder's host timeout/process-group guarantees.

The current canonical `invokeLifecycle` explicitly performs a cold CLI call and keeps its install checker local. Future integration is therefore control work: retain construction through execution, preserve the existing trusted checker, bind host bounds, and adapt actual receipt/close consumers. If shared harness source changes are selected, they belong in the existing runner/public-setup and maintained harness after B freezes; keep the explicit cold entry and reuse the existing check instead of copying its semantics.
