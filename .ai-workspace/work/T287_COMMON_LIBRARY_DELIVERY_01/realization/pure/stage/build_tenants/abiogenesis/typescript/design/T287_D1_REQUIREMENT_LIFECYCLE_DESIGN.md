### One canonical job, two identity domains

Add a closed, explicitly discriminated job-bound arm beside the existing fixed
declaration arm. Legacy inputs, declarations, checks and receipts keep their
meaning. The new installed declaration fixes source-role/schema constraints,
stage topology and dependencies, role-context rules, allowed realization/proof
contract refs, generic policy/shape templates, instruction assembly and bounded
worksite/command-construction capabilities. It fixes no scenario bytes, source
inventory digest, task/oracle digest, requirement ref, expected answer, target
path or scenario-specific policy text.

The root input is one closed SemanticJobInput value: complete source members
with logical locators/provenance and bytes; ordinary task and independent
evaluation data with their declared role visibility; and the owner's workspace
read/write/command bounds. Bounds may narrow the admitted invocation capability,
never enlarge it. Existing A/W/grant coordinates come from the actual admitted
environment/invocation, not an invented job workspace. User-specified paths in
ordinary source remain requirements to interpret, not a supplied Design asset.
The input contains no RequirementTerm, fulfillment binding, policy instance,
semantic asset, worksite target observation, generated prompt or worker answer.

The exact root raw-input admission owns this value. Every child/envelope carries
that same immutable job value and a derived coordinate anchored to root
invocation admission, raw-input ref/digest, installed lifecycle identity and
the admitted A/W/grant relation. Source inventory, task/evaluation digests and
source spans are projections of that value. They are not parallel mutable
authorities. Job-bound envelopes do not carry independently authoritative copies
of taskData, evaluationData or a substituted lifecycle. Runtime observations and
assets are additional admitted results, never modifications to the job.

Different requests have different job identities even though Product, Program,
schemas and topology remain byte-identical. A new invocation of equal input is
still separately admitted; equality of payloads does not confer another Run's
authority. Role projection may omit evaluation data from an author view without
changing the underlying job. Assessor context names the current assessed asset
and its actual eligible statement refs; predecessor and other-role views stay
context, not that field's domain.

### Assessed requirement binding and policy instances

Installed generic templates declare the allowed existing realization/proof
output contracts and minimum evidence roles/shared-basis/content constraints.
They describe what a lawful instance must carry; they contain no Hello/Add
requirement text. A policy instance supplies source-grounded job meaning, scope,
paired obligation and explicit unproved scope; a shape instance supplies the
job-specific content relation while retaining the template's minimum roles and
exact installed role-contract refs. Neither creates a schema, executable
predicate, implementation, effect, evaluator or new catalog member.

Use the existing finite requirement-refinement capability, extended with closed
binding proposals. A proposal names an existing grounded requirement or a local
candidate ref introduced by this same response; the Product owner resolves that
local ref to the canonical grounded term before assessor assembly. It selects
only installed allowed contracts and templates. Source quotes/spans are exact,
candidate refs unique, parent links valid, and paired obligations conserved.
No fixture maps prose labels to contracts or supplies a presolved requirement.

A binding version is a subordinate immutable value attached to the admitted
semantic result: job coordinate, stable requirement/obligation refs, monotonically
increasing version, exact prior-version ref/digest or initial-null marker,
existing four binding refs, policy/shape instance digests, introducing asset and
assessment source coordinates, and content-derived ref/digest. Source terms and
all earlier versions remain historical. The initial discovered null binding is
open, never construction-ready. A unique current version is projected from the
actual admitted same-job chain, not selected by largest number or a local map.

Product owns one pure instance/refinement projection reused by author candidate
construction, assessor context, assessment-result derivation and downstream
validation. ABG authenticates the input/result/assessment ancestry and invokes
that relation; it does not judge meaning. A satisfied independent assessment
must cover the exact proposed requirements and instances. Only its successful,
advancing native result makes the version available downstream. Falsified or
indeterminate assessment does not activate it. Same-version changed bytes,
missing/skipped/forked supersession, foreign jobs, unknown contracts/templates,
dropped mandatory roles or unexplained source substitution refuse.

Requirements readiness means source-grounded, independently assessed paired
obligations with admissible construction/proof bindings for the selected scope.
It is not realization or proof. Design may refine dependencies and construction
choices, not silently replace the assessed requirement instance. New or changed
binding meaning re-enters the native assessed refinement/D2 route. Any selected
obligation still null, conflicting or unassessed blocks its construction; source
coverage uncertainty remains explicit rather than being counted as fulfilled.

## Smallest carrier and ownership decision

Use one existing Program, GraphFunction and `C.of`, resolved from an installed
publication through ordinary Public invocation/result/replay. The new callable
is generic: it has no GLC stage names, Data Mapper identifiers or filesystem
paths in its implementation. Its declared effects are empty. Do not change
`retain_graph_input`, C1, C2, C3, the Public operation inventory or existing
worksite authority. The output contract is the future stage's ordinary input
contract; binding an actual semantic stage is the next dependent increment.

Add a closed, optional `requirementHandoffs` declaration collection to the
existing `ModulePublication`; a GraphFunction selects one declaration by its
existing string-reference `declarations` field. It is subordinate metadata,
not another published target, graph, catalog, ledger or Program. The first
carrier contains these typed projections of the owning GTL requirements:

| Declaration | Minimal first fields and meaning |
|---|---|
| Handoff declaration | Stable declaration ref; selected GF ref; source context ref; required input-role ref; ordered term and fulfillment-binding refs. All references resolve inside this immutable publication. |
| `ContextDeclaration` | Stable context ref, source locator and inventory digest; full member inventory with member ref, relative logical path, exact byte count and SHA-256. The source role is declared independently of invocation input. |
| `RequirementTerm` | Stable requirement ref and source bindings: context/member refs, member digest, half-open UTF-8 byte span and span digest. The selected first witness binds REQ-ACC-01..05; the remaining full source remains present and semantically unassessed. |
| `GtlContractFulfillmentBinding` | Stable obligation ref and requirement ref, realization-output contract ref, proof-output contract ref and proof-policy/shape refs. These declare the required pairing; they are not evidence, fulfillment or closure. |

There is no current implementation of these three GTL types. This introduces
their bounded native declaration subset, reusing the required fulfillment
binding concept instead of introducing a second pair-list algebra. More fields
for general relations, spans, asset surfaces, routing, depth and discovered
obligations remain explicit later dependencies. Unknown fields/ref kinds are
refused; this subset must not silently accept those unsupported declarations.
Missing proof policy/shape is represented as a typed non-closing gap; no default
policy is inferred. Every selected requirement still receives both obligation
roles, even when a role's required contract/policy is unresolved.

The independently admitted publication fixes the source inventory, role, term
vector and bindings. The request supplies exact source bytes (canonical base64
per member), source-role ref and selected declaration ref. It cannot supply an
alternative expected inventory, filter the selected terms or set coverage.
Duplicate, missing, extra or changed members, wrong role, wrong declaration or
source/span digest, dangling refs, duplicate identities and mismatched binding
roles fail closed before an admitted success. Byte hashing uses the decoded
bytes, without Unicode or line-ending normalization; paths identify source
members and confer no filesystem read/write authority.

The fixed publication is not itself proof that somebody captured every user
requirement correctly. In the installed witness, its exact declaration basis
is pinned to the independently accepted GLC five-file inventory and user-role
selection before invocation. Mutating the request and its claimed manifest
together cannot replace that basis. Replacing the publication is a different
declared subject requiring a new admission/disposition, not a passing negative
test. Unresolved source authority or semantic completeness remains visible.

## Native declaration access, admission and replay

`LeafExecutionOccurrence` currently has no generic declaration basis. Its

not be cast or widened into source authority. Add one optional read-only
declaration-basis projection for the new F_D binding. Existing leaves receive

projection. The deterministic leaf reads the selected declaration from it,
checks the request against it and returns an ordinary realization candidate.
No declaration authority is accepted from the JSON request.

The native owner validates the result against the same admitted input and
declaration basis. It must regenerate/compare the exact source identities,
selected term vector and paired obligations, not merely validate output shape.
An omitted obligation or altered role cannot pass by a leaf returning a
well-formed smaller result. Resolve/validate the basis with existing ABG
execution-basis and prefix machinery; no second store, process-local authority
brand or writable requirement ledger is permitted.

Existing ABG input/result admission facts carry the typed transfer input and
result. The leaf return alone is unadmitted. Reuse existing C-call/result/Run
event ownership, durable bytes and fresh result/replay operations. A returned
handoff contains the full source bytes and fixed inventory; source-role and
declaration identity; the immediate admitted input/basis identity; exact terms
and paired role obligations; and a typed gap projection. Copying source bytes
into an arbitrary JSON property is insufficient without these native checks.
For this first invocation the admitted input is the predecessor; no semantic
stage result is fabricated and no previous run is relabelled as one.

The gap projection is read-only and always non-closing. It reports each selected
realization/proof role as lacking admitted evidence, unresolved policy/shape
where applicable, and the remaining semantic-source assessment, instruction
assembly, stage-result, depth/strength and discovery dependencies. It has no
eligible/fulfilled branch and no caller-set pass flag. These are facts about
this transfer's limited coverage, not an additional closure state machine.
The existing Run may close because the exact handoff succeeded; application
requirement obligations remain open. No `EdgeFulfillmentLedgerRow` for those
application requirements may be manufactured from the transfer judgment.

This first typed admitted result is not a claim that the general Requirement
Ledger, requirement-event family, coverage/depth fold or native continuation
integration is implemented. Those remain dependencies before their outcomes
can be claimed. Queries remain projections of admitted events, not lazy writes.
