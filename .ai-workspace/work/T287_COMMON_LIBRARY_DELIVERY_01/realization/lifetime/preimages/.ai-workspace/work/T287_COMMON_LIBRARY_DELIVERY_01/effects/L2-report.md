### Callable contract and irreducible remainder

One callable `createOwnedProcessLifetime(child, bounds, observations)` returns an ephemeral handle with `requestTermination(mode)` and one completion promise. A private implementation may split pure observation/state reduction from effect scheduling, but callers must not regain separate signal/probe/escalation loops.

1. **Domain and ownership.** `child` is the actual freshly spawned Node child for one attempt; the caller establishes detached group ownership on POSIX or direct-child scope on Windows. Bounds are positive finite integers supplied by the declared owner. This primitive does not spawn, choose a command, discover an executable, alter environment, own admission, lease policy or HTTP policy. A process escaping its POSIX group is outside this physical scope; do not label group absence as universal descendant absence.
2. **Physical facts remain separate.** Completion exposes direct exit observation/status/signal, launch failure, scope kind, scope absence (`absent | present | unknown`), close observed, bounded stream disposal/drain, and first callback error. Undefined PID plus confirmed spawn failure is “no child established,” not a fabricated exit. `ESRCH` can establish POSIX group absence; permission/probe errors cannot. Windows can establish the direct child fact, not POSIX group/descendant facts.
3. **Lifecycle.** Attach actual error/exit/close observation immediately to the spawned child. A direct exit initiates owned-scope cleanup even if streams close. Ordinary cleanup checks scope, requests TERM, waits the declared grace, requests KILL if still needed, then observes only through a declared confirmation bound. Close and absence are independent. A final bounded drain/disposal ends observation; unresolved scope remains unknown/present. Resolve once, clear timers/listeners, and preserve actual physical-close facts. Calls to request termination coalesce into the same attempt; immediate cleanup may strengthen graceful cleanup but cannot extend its final bound.
4. **Explicit observation ordering.** Normal signal-request notification precedes physical signal; direct-exit notification precedes completion; unconfirmed notification precedes final owner projection. Hooks report facts only. If a callback throws, retain the first error, disable further ordinary callbacks, perform bounded emergency cleanup, and return/rethrow that original failure according to the caller's existing interface. Do not replace it with a cleanup or observer error or claim that an unrecorded ABG event was admitted.
5. **Streams and result boundary.** Worker and command callers preserve their existing direct-exit capture cut, including the worker's pre-cleanup `resultBearingStdout` snapshot. The common mechanism may dispose actual streams, but must not admit descendant output after the owner's result boundary. The HTTP adapter must state and test its analogous capture boundary; response/port observations already made remain observations, not evidence that the scope terminated.
6. **Owner projections are not unified.** Current worker `finishTermination` reports `terminationConfirmed = scopeConfirmed && observedExit !== null`; current command completion can report physical scope confirmation even when direct exit is not yet observed, including no-child launch failure. Preserve those existing mappings separately. Do not make one shared Boolean and accidentally widen either contract. HTTP uses the actual scope/launch/exit facts to replace its constant `true`; status, timeout and HTTP response remain separate fields.
7. **Failure before/after effect.** Invalid bounds/ownership setup refuses before applying signals; launch failure records no established child. Once launched, failed cleanup is a bounded observation with uncertainty, not rollback. A timeout is declared owner policy; the primitive cannot infer retry, continuation, successful C closure, or whether an HTTP response satisfies its predicate.
8. **Resource lifetime.** Handle, listeners and timers belong to this one attempt and cannot be serialized or cached as authority. `activeCommand` in the helper remains set until lifetime completion, not merely launcher close. Owner heartbeat/deadline timers are cleared in `finally`, including owner-side filesystem/HTTP/callback exceptions. Emergency parent SIGTERM/SIGINT handling remains a distinct best-effort signal path; parent exit cannot certify child cleanup.

**HTTP bounded-owner decision:** after launch, its owner must always finalize through this primitive on normal response, invalid/missing port, request failure, direct exit and unexpected owner exception. Preserve the existing observable request/response/port diagnostics; record truthful termination uncertainty. A successful observation carrier may describe a failed/uncertain inner process: it must not be silently relabeled as Product outcome success or quiescence. No new event type or public failure schema is selected here.

**Budget obligation:** `product/worksite_command_execution.ts::projectWorksiteCommandExecutionBudget`, lines 145–171, currently budgets command timeout plus two grace terms, but HTTP launch timeout plus only one grace term and request timeout. The HTTP algorithm must budget its selected bounded confirmation and drain explicitly. Use the same two grace phases as the common cleanup and account for bounded drain (currently `min(grace, 250)`) in the declared rule/calculation; do not hide extra per-command/per-probe time in the single 5,000 ms owner allowance. Preserve strict less-than comparisons and absolute > inactivity ordering. Budget boundary/refusal tests are part of E03, not an optional optimization.
